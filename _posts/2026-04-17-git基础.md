## Git基础概念

### 为什么需要分支

分支的本质是创建一条独立发展的"平行时间线"，而非复制代码。它的逻辑类似RPG游戏的"开新存档"：

* **主分支（main/master）**：主线剧情存档，始终保持稳定可用的版本。
* **功能分支（feature branch）**：支线任务存档，用于开发新功能，互不干扰。
* **修复分支（hotfix branch）**：紧急存档，用于随时切出修复线上bug。

通过分支，开发者可以：
- 同时推进多项任务
- 随时中断当前工作去修bug
- 安全试验新方案（失败直接删除分支）
- 支持团队成员在各自分支上并行开发

### 分支基础操作

#### 查看与创建
- 查看当前分支（带 `*` 号的为当前分支）：`git branch`
- 创建新分支（仅创建，不切换）：`git branch <分支名>`

#### 切换与创建并切换
- 切换分支（工作区代码会自动变为该分支的状态）：`git checkout <分支名>` 或 `git switch <分支名>`
- 创建并立即切换（最常用方式）：`git checkout -b <分支名>` 或 `git switch -c <分支名>`

#### 在分支上工作

在功能分支上的新增提交（如新增文件、修改代码）仅存在于该分支的时间线上，不影响主分支。切换回主分支时，这些改动会在工作区隐藏；切回功能分支，改动又会恢复。

## 环境配置与安全拉取

### 安全拉取项目 (Clone)

很多新人入职第一天卡在这里：有权限但拉不下来代码。这通常是因为还在用 HTTPS 这种老旧方式。

#### 场景模拟：入职第一天

组长给你发了一个仓库地址：`git@gitlab.company.com:backend/api-service.git`。
你直接复制去下载，结果报错：`Permission denied (publickey)`。

#### 正确步骤：配置 SSH Key

这是为了让公司服务器认识你的电脑（相当于录入指纹），配置一次，永久有效。

```bash
# 1. 在终端输入生成命令 (一路回车即可)
ssh-keygen -t ed25519 -C "your_email@company.com"

# 2. 查看并复制生成的公钥 (Windows 使用 type, Mac 使用 cat)
cat ~/.ssh/id_ed25519.pub
ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAI... (复制这一长串)
```

最后一步：打开公司 GitLab/GitHub 网页 -> 点击头像 -> Settings -> SSH Keys -> 粘贴进去并保存。

现在，执行拉取：
```bash
git clone git@gitlab.company.com:backend/api-service.git
Cloning into 'api-service'... done.
```

### 远程协作基础

团队协作需将本地分支与远程仓库（如GitHub）同步：

* **关联远程仓库**：`git remote add origin <远程仓库URL>`（origin为远程仓库别名）
* **推送到远程**：`git push -u origin <分支名>`（`-u` 即 `--set-upstream`，建立本地与远程分支的追踪关系，设置后后续只需 `git push`）
* **拉取远程更新**：`git pull`（相当于 `git fetch` + `git merge`，拉取并合并远程更新到当前分支）
* **克隆远程仓库**：`git clone <远程仓库URL>`（首次获取项目，包含完整代码和历史记录）
* **拉取远程特定分支到本地**：`git fetch origin` 然后 `git switch -c <本地分支名> --track origin/<远程分支名>`

## 日常开发流程

### 标准开发流程 (Daily Workflow)

#### 场景模拟：修改登录页标题

任务：把 index.html 里的标题从 "Welcome" 改成 "Hello"。

#### Step 1: 检查状态
```bash
git status
modified: index.html
```
只要是红色的文件名，说明 Git 发现了修改但还没受理

#### Step 2: 加入暂存区 (Add)
```bash
git add index.html
```
再次 `git status` 会变成绿色，说明已经放入"发货箱"

#### Step 3: 提交存档 (Commit)
```bash
git commit -m "feat: 更新首页标题文案"
[main 2f3a1c] feat: 更新首页标题文案
```

### 分支开发与合并

#### 合并分支

功能开发完成后，需将其合并回主分支：

1. 切换到目标分支（如主分支）：`git switch main`
2. 执行合并：`git merge <功能分支名>`
3. 如果主分支在创建功能分支后没有新提交，Git会执行**快进合并**，直接将主分支指针移动到功能分支的最新提交节点。

#### 删除分支

合并后，不再需要的功能分支可被清理：

* 安全删除（仅删除已合并的分支）：`git branch -d <分支名>`
* 强制删除（删除未合并的分支）：`git branch -D <分支名>`

## 合并策略：Merge vs Rebase

### 核心难点：Merge 还是 Rebase？

这是小白最容易混淆的地方。两者都是"合并代码"，但结果完全不同。

#### 场景模拟

你在 feature 分支开发，同时同事在 main 分支提交了新代码。现在你需要更新你的分支，把同事的代码同步进来。

### Method A: Git Merge

```
同事的提交
    ↓
你的提交
    ↓
合并节点
```

```bash
git merge main
```

特点：保留完整历史，但会生成一个额外的"合并节点"，导致历史线分叉、像渔网一样乱。

### Method B: Git Rebase (变基)

```
同事的提交
    ↓
你的提交(被移到这里)
```

```bash
git rebase main
```

特点：把你的提交"剪切"下来，"粘贴"到同事最新提交的后面。历史线是一条直线，非常干净。

### ⚠️ 黄金法则：

1. 在自己的私有分支上（别人不用的），为了保持整洁，尽量用 Rebase。
2. 在公共分支上（如 main/dev），绝对禁止使用 Rebase，必须用 Merge。

## 冲突解决

### 手把手解决冲突

#### 场景模拟

你和同事小李都修改了 config.js 的第 3 行。
小李改成了 `timeout = 5000` 并先推送了。
你改成了 `timeout = 3000`，拉取时报错：`CONFLICT (content): Merge conflict in config.js`。

#### Step 1: 打开代码编辑器

你会看到如下乱码，不要怕，这是 Git 在问你选哪个：

```bash
<<<<<<< HEAD
const timeout = 3000; // 你的代码
=======
const timeout = 5000; // 小李的代码 (Incoming)
>>>>>>> 4a5b6c...
```

#### Step 2: 修改代码

直接删除那些 `<<<` `===` `>>>` 符号，保留你认为正确的数值（比如协商后决定用 5000）。

```bash
const timeout = 5000;
```

#### Step 3: 告诉 Git 你修好了

```bash
git add config.js
# 如果是 merge 产生的冲突：
git commit -m "fix: 解决超时时间冲突"
# 如果是 rebase 产生的冲突：
git rebase --continue
```

## 错误恢复与忽略文件

### 救命药丸：写错了怎么办？

#### 场景 A: 只是写乱了，还没 add

"把文件还原成上次提交的样子，我刚写的都不要了。"

```bash
git checkout .
```

#### 场景 B: 已经 add 了，但不想 commit

"哎呀，多添加了一个文件到暂存区。"

```bash
git reset HEAD file.txt
```

#### 场景 C: 已经 commit 了，想撤销这次提交

"刚才提交的代码有 Bug，我要撤销这次提交，但保留代码让我再改改。"（最常用）

```bash
git reset --soft HEAD~1
```
`--soft` 意思是：撤销提交记录，但保留文件修改在暂存区

### 忽略文件配置 (.gitignore)

有些文件永远不应该上传到仓库，比如：密码文件、操作系统缓存、巨大的 node_modules、日志文件。

#### 场景模拟：门卫机制

Git 有一个门卫叫 `.gitignore`。如果你把文件名写在里面，Git 就会假装看不见它们，`git status` 不会提示，`git add` 也不会添加。

#### 如何配置？

在项目最外层新建一个名为 `.gitignore` 的文件（注意前面有个点），写入以下内容：

```bash
# 1. 忽略系统生成文件
.DS_Store
Thumbs.db

# 2. 忽略依赖包 (体积巨大，必须忽略)
node_modules/
dist/

# 3. 忽略环境变量与密钥 (安全第一！)
.env
secret.key

# 4. 忽略日志
*.log
```

#### ⚠️ 救命：我忽略了，但它还是被上传了？

原因：文件在添加进 `.gitignore` 之前已经被 Git 追踪了。
解决办法：必须先从 Git 缓存中删除它。

```bash
git rm -r --cached .
# 清除所有缓存
git add .
# 重新添加，此时 .gitignore 才会生效
git commit -m "fix: 重置忽略规则"
```

## 团队协作流程

### 最小可运行团队协作流程

一套标准且闭环的多人协作开发流程如下：

1. **克隆项目**：`git clone <URL>` 并进入项目目录。
2. **创建功能分支**：`git switch -c feature-register`
3. **本地开发与提交**：编写代码后，`git add .` 与 `git commit -m "添加用户注册功能"`
4. **推送到远程**：`git push -u origin feature-register`
5. **继续开发与推送**：后续提交只需 `git push`
6. **合并到主分支**：`git switch main` -> `git pull`（拉取最新代码）-> `git merge feature-register` -> `git push`
7. **清理分支**：本地删除 `git branch -d feature-register`，远程删除 `git push origin --delete feature-register`

### 分支命名规范

为了团队协作清晰，分支应按规律命名：

* `feature/功能名`：新功能开发（如 `feature/user-profile`）
* `bugfix/问题描述`：常规bug修复
* `hotfix/紧急修复`：线上紧急修复（如 `hotfix/payment-crash`）
* `refactor/重构内容`：代码重构

### 切换分支前有未提交的修改怎么办？

若修改会与目标分支冲突，Git会阻止切换。两种处理方式：

* **提交修改**：`git add .` -> `git commit -m "暂存"` -> 切换分支
* **暂存修改**：使用 `git stash` 将修改临时隐藏，工作区变干净后切换分支；处理完其他事务切回后，使用 `git stash pop` 恢复修改。

### 分支太多如何清理？

定期查看并清理已合并的分支：`git branch --merged` 查看已合并列表，随后使用 `-d` 和 `--delete` 清理本地与远程分支。

### 误删分支如何恢复？

利用引用日志找回：执行 `git reflog` 找到删除前的 commit ID，然后通过 `git checkout -b <新分支名> <commit-id>` 恢复。

## 实战案例：开发者的一天

这里模拟从接到需求到代码上线的全过程。请按顺序执行。

### 09:00 AM - 接到新需求

任务：开发"联系我们"页面 (contact.html)。
原则：永远不要在 main 分支直接写代码，第一件事是切新分支。

```bash
# 1. 确保主分支是最新的
git checkout main
git pull

# 2. 创建并切换到新分支
git checkout -b feat/contact-page
```

### 10:30 AM - 沉浸式开发

你在项目中新建了 contact.html 并写完了代码。现在需要保存。

```bash
git status
Untracked files: contact.html

git add .
git commit -m "feat: 新增联系我们页面"
```

### 11:00 AM - 突发状况：主线变了

准备提交时，发现同事刚刚向 main 分支推送了公共组件更新。你需要把这些更新"同步"到你的分支里。

关键点：此时使用 Rebase 让历史更干净。

```bash
# 1. 抓取远程最新变动 (不合并，只下载)
git fetch origin main

# 2. 变基：把你的提交"嫁接"到最新代码后面
git rebase origin/main
Successfully rebased and updated refs/heads/feat/contact-page.
```

### 11:15 AM - 提交上线

本地测试通过，代码是最新的，历史是干净的。发射！

```bash
git push origin feat/contact-page
```

之后去 GitLab/GitHub 网页上点击 "Create Merge Request" 即可。

## 最佳实践与常见问题

### Git 工作流总结

1. **初始化项目**
   - 首次使用：配置 SSH Key，使用 `git clone` 拉取代码
   - 创建项目：`git init`，添加远程仓库，推送初始代码

2. **日常开发**
   - 创建功能分支：`git checkout -b feature/xxx`
   - 开发并提交：`git add .` + `git commit -m "描述"`
   - 同步远程更新：`git pull` 或 `git rebase`

3. **合并与发布**
   - 推送到远程：`git push`
   - 创建合并请求
   - 合并后清理分支

4. **错误处理**
   - 未提交的修改：`git checkout .` 或 `git stash`
   - 已添加的文件：`git reset HEAD`
   - 已提交的修改：`git reset --soft HEAD~1`
   - 冲突解决：手动编辑 + `git add` + `git commit` 或 `git rebase --continue`

### 团队协作建议

1. **保持提交信息清晰**
   - 使用语义化的提交前缀：feat、fix、docs、style、refactor、test、chore
   - 提交信息简洁明了，说明"做了什么"和"为什么"

2. **定期同步远程代码**
   - 开发前先拉取最新代码
   - 避免长时间不同步导致冲突

3. **合理使用分支**
   - 功能开发使用独立分支
   - 及时合并并删除已完成的分支
   - 遵循团队统一的分支命名规范

4. **妥善处理冲突**
   - 遇到冲突不要慌张
   - 仔细比较不同版本的代码
   - 与同事协商确定最终方案

5. **保护主分支**
   - 主分支始终保持可运行状态
   - 重要功能通过合并请求合并
   - 使用 CI/CD 确保代码质量
