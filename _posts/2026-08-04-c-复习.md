## 一、C++ 编译流程

```
预处理 → 编译 → 汇编 → 链接
```

### 1. 预处理（Preprocessing）

- 处理 `#include`（头文件展开，递归地将头文件内容复制到当前文件）
- 处理 `#define`（宏替换，纯文本替换，不涉及类型检查）
- 处理 `#ifdef` `#ifndef` `#endif` 等条件编译指令
- 删除注释
- 输出：展开后的 `.i` 文件（C 语言）或 `.ii` 文件（C++）

```bash
g++ -E main.cpp -o main.ii   # 只预处理
```

### 2. 编译（Compilation）

- 将预处理后的文件翻译为**汇编代码**（`.s` 文件）
- 主要步骤：
  - **词法分析**：将源代码字符序列分割为 token（关键字、标识符、字面量等）
  - **语法分析**：将 token 按语法规则生成具体语法树（CST），再化简为抽象语法树（AST）
  - **语义分析**：类型检查、函数/变量声明与使用匹配、作用域解析
  - **优化**：基于 AST/中间表示（IR）进行优化（常量折叠、死代码消除、内联等）
  - **代码生成**：将优化后的 IR 翻译为目标平台的汇编代码
- CST 是一颗包含所有语法信息的稠密树，包含所有 token（括号、分号等），完整反映运算符优先级。AST 丢掉 CST 中的语法噪音，只保留语义结构，不包含括号等纯语法信息，优先级由树的结构本身隐含。

```bash
g++ -S main.ii -o main.s   # 只编译到汇编
```

### 3. 汇编（Assembly）

- 将汇编代码翻译为**机器码**，生成**可重定位目标文件**（`.o` / `.obj`）
- `.o` 文件中包含：机器指令、数据段、符号表（记录了本文件定义的和引用的外部符号）、重定位信息

```bash
g++ -c main.s -o main.o     # 汇编为目标文件
# 或直接从源码：
g++ -c main.cpp -o main.o
```

### 4. 链接（Linking）

- 将多个 `.o` 文件和库文件合并为**可执行文件**
- 核心任务：**符号解析**（把每个符号引用与其唯一定义关联）+ **重定位**（修正地址）
- 分为：
  - **静态链接**：将库代码直接复制到可执行文件中（`.a` / `.lib`），文件大但部署简单
  - **动态链接**：运行时加载共享库（`.so` / `.dll`），文件小、共享内存、可热更新

```bash
g++ main.o utils.o -o program           # 链接多个 .o
g++ main.cpp -o program                 # 一键编译+链接
g++ main.cpp -L/path/to/lib -lmylib -o program  # 链接自定义库
```

| 阶段   | 输入        | 输出       | 关键操作                     |
| ------ | ----------- | ---------- | ---------------------------- |
| 预处理 | `.cpp` `.h` | `.ii`      | `#include` 展开、宏替换      |
| 编译   | `.ii`       | `.s`       | 词法/语法/语义分析，生成汇编 |
| 汇编   | `.s`        | `.o`       | 汇编→机器码，生成符号表      |
| 链接   | 多个 `.o`   | 可执行文件 | 符号解析 + 重定位            |

## 二、多态及面向对象核心机制

### 2.1 面向对象三大特性

| 特性 | 核心思想                     | C++ 实现方式                   |
| ---- | ---------------------------- | ------------------------------ |
| 封装 | 隐藏内部实现，暴露接口       | `private`/`protected`/`public` |
| 继承 | 复用父类代码，建立"is-a"关系 | `class B : public A {};`       |
| 多态 | 同一接口，不同行为           | 虚函数 + 模板重载（见下文）    |

### 2.2 多态的两种形式

#### 静态多态（编译时多态）

在编译期确定调用哪个函数，无运行时开销。

**① 函数重载（Function Overloading）**

```cpp
// 同一作用域内，函数名相同，参数列表不同（类型/个数/顺序）
void print(int x);
void print(double x);
void print(int x, int y);
// 注意：返回值类型不同不能构成重载！
```

重载决议规则（优先级从高到低）：
1. 精确匹配
2. 提升匹配（如 `char` → `int`）
3. 标准转换匹配（如 `int` → `double`）
4. 用户定义转换（转换构造函数/类型转换运算符）

**② 运算符重载（Operator Overloading）**

```cpp
class Complex {
public:
    double real, imag;
    Complex operator+(const Complex& other) const {
        return {real + other.real, imag + other.imag};
    }
};
```

**③ 模板（Templates）**

```cpp
template <typename T>
T max(T a, T b) { return a > b ? a : b; }
// 编译器根据调用参数自动生成对应类型的版本（实例化）
```

#### 动态多态（运行时多态）

通过**虚函数**实现，在运行时根据对象的实际类型决定调用哪个函数。

```cpp
class Animal {
public:
    virtual void speak() { cout << "Animal" << endl; }
    virtual ~Animal() {}  // ★ 虚析构函数（见下文）
};

class Dog : public Animal {
public:
    void speak() override { cout << "Woof!" << endl; }  // C++11 override
};

Animal* a = new Dog();
a->speak();  // 输出 "Woof!" —— 运行时多态
```

### 2.3 虚函数底层原理：虚函数表（vtable）

```
对象内存布局：
┌─────────────────┐
│  vptr (8 bytes)  │ ──→ ┌──────────────────┐
├─────────────────┤     │ type_info (RTTI)  │
│  成员变量...     │     ├──────────────────┤
│                  │     │ Dog::speak       │  ← 虚函数表 (vtable)
└─────────────────┘     │ Animal::~Animal  │
                         └──────────────────┘
```

- 每个**包含虚函数的类**有一张**虚函数表**（vtable），存储该类所有虚函数的地址
- 每个**对象**有一个**虚指针**（vptr），指向所属类的 vtable
- 调用虚函数时：`obj.vptr → vtable → 函数地址 → 调用`
- **代价**：一次额外的间接寻址（通常可忽略）+ 每个对象多 8 字节（64 位系统）

### 2.4 纯虚函数与抽象类

```cpp
class Shape {
public:
    virtual double area() const = 0;  // 纯虚函数 —— 没有实现，子类必须重写
    virtual ~Shape() {}
};

// Shape s;  // ❌ 编译错误：不能实例化抽象类

class Circle : public Shape {
    double r;
public:
    double area() const override { return 3.14159 * r * r; }
};
```

- 包含纯虚函数的类 = **抽象类**，不能实例化
- 子类必须实现**所有**纯虚函数，否则自己也成为抽象类
- 纯虚函数可以有实现（`virtual void f() = 0;` 然后 `void Base::f() {}`），子类可显式调用 `Base::f()`

### 2.5 C++ 中的"接口"

C++ 没有 Java/C# 那样的 `interface` 关键字，而是用**只有纯虚函数的抽象类**来充当接口：

```cpp
// C++ 接口：只定义"能做什么"，不定义"怎么做"
class IShape {                         // 命名习惯：前缀 I = Interface
public:
    virtual double area() const = 0;
    virtual double perimeter() const = 0;
    virtual void draw() const = 0;
    virtual ~IShape() {}               // 虚析构，保证子类正确释放
};

class Circle : public IShape {         // "实现"接口（也是继承语法）
    double r;
public:
    double area() const override { return 3.14159 * r * r; }
    double perimeter() const override { return 2 * 3.14159 * r; }
    void draw() const override { /* ... */ }
};
```

**接口 vs 实现基类**：

|               | 接口（纯抽象类）           | 普通基类                    |
| ------------- | -------------------------- | --------------------------- |
| 成员函数      | 全是纯虚函数，没有方法体   | 可以有具体实现              |
| 成员变量      | 没有（仅 static const）    | 可以有                      |
| 目的          | 定义"**能做什么**"的契约   | 提供**公共实现**供复用      |
| 对应关系      | 可实现多个接口（多继承）   | 一般单继承                  |
| 耦合度        | 低（只约定行为）           | 高（共享实现细节）          |

> 🌟 **核心洞见**：**接口 = 契约**。`IShape` 告诉所有使用者"我保证有 area()、perimeter()、draw() 这三个方法"，至于怎么实现的，使用者根本不需要关心。这就是"面向接口编程"的含义。

### 2.6 组合 vs 继承

**继承**是 "is-a" 关系（狗**是**动物），**组合**是 "has-a" 关系（车**有**引擎）。C++ 中优先使用组合。

```cpp
// ❌ 滥用继承：只是为了复用 Vector 的代码
class Stack : public std::vector<int> {
    // Stack 继承了 push_back/operator[] 等所有方法
    // 破坏封装！使用者可以直接 v[5] 随机访问，绕过了栈的 LIFO 语义
};

// ✅ 用组合：Vector 作为内部成员
class Stack {
    std::vector<int> data_;
public:
    void push(int x) { data_.push_back(x); }
    int pop()       { int x = data_.back(); data_.pop_back(); return x; }
    // 只暴露栈应有的接口，不暴露 vector 的所有方法
};
```

|          | 继承（is-a）                | 组合（has-a）                 |
| -------- | --------------------------- | ----------------------------- |
| 关系     | "A 是 B 的一种"             | "A 包含 B 作为一部分"         |
| 访问级别 | 子类能访问父类的 protected  | 只能通过成员对象的 public 接口 |
| 耦合度   | 高（白盒复用，知道父类内部）| 低（黑盒复用，只知道接口）     |
| 运行时   | 不能更换父类                | 可以动态替换成员对象           |
| 复用方式 | 继承行为 + 可重写           | 委托给成员对象                 |

> 🌟 **原则**：能用组合就用组合。需要运行时多态（基类指针/引用调用子类方法）时才用继承。

### 2.7 虚析构函数 —— 非常重要！

```cpp
class Base {
public:
    virtual ~Base() { cout << "~Base" << endl; }  // ★ 必须是 virtual
};

class Derived : public Base {
    int* data;
public:
    Derived() : data(new int[100]) {}
    ~Derived() override { delete[] data; cout << "~Derived" << endl; }
};

Base* ptr = new Derived();
delete ptr;  // 如果 ~Base() 不是 virtual，只调用 ~Base()，data 泄漏！
// 输出：~Derived → ~Base  （正确释放）
```

> 🌟 **记忆口诀**：只要一个类被设计为基类（有虚函数/会被继承），就把析构函数声明为 `virtual`。如果一个类不会被继承，用 `final` 标记。

### 2.8 继承类型

| 继承方式       | 父类 public 成员 | 父类 protected 成员 | 父类 private 成员 |
| -------------- | ---------------- | ------------------- | ----------------- |
| public 继承    | public           | protected           | 不可访问          |
| protected 继承 | protected        | protected           | 不可访问          |
| private 继承   | private          | private             | 不可访问          |

90% 的情况用 `public` 继承（is-a 关系）。`private` 继承 = has-a（组合通常更好）。

### 2.9 构造/析构调用顺序

```cpp
class A { };
class B : public A {
    C member;  // 成员对象
};
B b;
```

**构造顺序**（从外到内 → 从内到外）：
1. 基类构造函数（`A()`）
2. 成员对象构造函数（按声明顺序，`C()`）
3. 自身构造函数体（`B()`）

**析构顺序**：严格按构造的逆序（3 → 2 → 1）

> ⚠️ 构造函数和析构函数中调用虚函数，调用的是**当前类自己的版本**，不是子类的（此时子类还没构造完/已经析构了）。

### 2.10 C++11 override 与 final

```cpp
class Base {
public:
    virtual void f(int) {}
    virtual void g() {}
};

class Derived : public Base {
public:
    void f(int) override {}   // ✅ 明确告知这是重写，编译器会检查签名是否匹配
    // void f(double) override {}  // ❌ 编译错误：父类没有 virtual void f(double)
    void g() final {}          // 禁止子类进一步重写
};

class More : public Derived {
    // void g() override {}  // ❌ 编译错误：Derived::g 是 final
};
```

### 2.11 虚继承（菱形继承）

```cpp
class A { public: int x; };
class B : virtual public A {};  // 虚继承
class C : virtual public A {};
class D : public B, public C {};  // D 中只有一份 A::x
```

- 解决的问题：菱形继承中，最底层类有**多份**顶层基类成员
- 代价：额外的间接指针（vbptr），访问稍慢
- 一般建议：**优先用组合代替多继承**，真需要多继承时考虑虚继承

## 三、常见报错

### 3.1 编译错误（Compile Errors）

| 错误类型     | 典型信息                                        | 常见原因                                   |
| ------------ | ----------------------------------------------- | ------------------------------------------ |
| 语法错误     | `expected ';' before ...`                       | 少了分号/括号/花括号                       |
| 未声明标识符 | `'xxx' was not declared in this scope`          | 忘记 `#include` 或拼写错误或命名空间问题   |
| 类型不匹配   | `cannot convert 'A' to 'B'`                     | 函数参数/赋值类型不对                      |
| 重复定义     | `redefinition of 'class X'`                     | 头文件缺少 `#pragma once` 或 include guard |
| 模板错误     | 一长串模板展开错误                              | 类型不满足模板约束                         |
| 缺少返回值   | `no return statement in function returning ...` | 非 void 函数没有 return                    |

### 3.2 链接错误（Linker Errors）

**`undefined reference to 'xxx'`** —— 最经典的链接错误。

```cpp
// main.cpp
void foo();          // 声明了但没找到定义
int main() { foo(); }
// → undefined reference to 'foo()'
```

| 原因                                   | 解决方式                                             |
| -------------------------------------- | ---------------------------------------------------- |
| 只声明了函数，忘了实现                 | 补上函数体                                           |
| 忘记链接 `.cpp` 文件或库               | `g++ main.cpp foo.cpp` 或 `-l<lib>`                  |
| 在 `.cpp` 中调用了模板，定义在别处     | 模板定义必须放在头文件中（编译期实例化需要完整定义） |
| 头文件中的 `inline` 函数没在头文件定义 | 把实现移到头文件                                     |
| C/C++ 混用导致符号名不匹配             | 用 `extern "C"` 包裹                                 |

**`multiple definition of 'xxx'`** —— 函数/变量被定义了多次。

| 原因                              | 解决方式                                                |
| --------------------------------- | ------------------------------------------------------- |
| 头文件中定义了非 inline 函数/变量 | 改为声明，定义移到 `.cpp`，或用 `inline`                |
| 多个 `.cpp` 包含了同一个实现文件  | 检查构建系统，避免重复编译同一实现文件                  |
| 缺少 include guard                | 添加 `#pragma once` 或 `#ifndef` / `#define` / `#endif` |

### 3.3 运行时错误（Runtime Errors）

**Segmentation Fault（段错误）** —— 访问了不该访问的内存。

```cpp
// 常见原因：
int* p = nullptr;
*p = 42;                    // 空指针解引用

int* p = (int*)0xDEADBEEF;  // 野指针
*p = 42;

int arr[10];
arr[100] = 42;               // 数组越界

char* s = "hello";
s[0] = 'H';                  // 修改字符串字面量（只读内存）

int* p = new int[10];
delete[] p;
p[0] = 42;                   // 使用已释放的内存（use-after-free）

int* f() { int x = 0; return &x; }  // 返回局部变量的地址（悬空指针）
```

**Stack Overflow（栈溢出）**：

```cpp
// 原因1：无限递归
void f() { f(); }

// 原因2：局部变量太大（栈通常 8MB）
void g() { int arr[10000000]; }  // 远超栈空间

// 解决：用堆分配（new / std::vector）或迭代代替递归
```

**内存泄漏（Memory Leak）**：

```cpp
void leak() {
    int* p = new int[100];
    // 忘记 delete[] p;
}  // p 指针销毁了，但内存还在，再也找不回来了

// 解决：用 RAII（智能指针、STL 容器）
void safe() {
    std::vector<int> v(100);    // 自动释放
    std::unique_ptr<int[]> p(new int[100]);  // 自动释放
}
```

### 3.4 未定义行为（Undefined Behavior，UB）

编译器可以**做任何事**——包括"看起来正常"，这是最危险的。

```cpp
int i = 0;
i = i++ + ++i;           // UB：同一表达式多次修改同一变量

int x = 42;
int y = 0;
int z = x / y;           // UB：除零

int a = INT_MAX;
a += 1;                  // UB：有符号整数溢出

const int& ref = 42;     // OK：const 引用延长临时对象生命周期
int& ref2 = 42;          // ❌ 编译错误（幸好）

auto* p = new int[10];
delete p;                // UB：new[] 必须用 delete[]，反之亦然
```

> 🌟 **核心教训**：用智能指针和 STL 容器代替裸指针和 C 数组，能消除 90% 的内存相关错误。

### 3.5 迭代器失效

```cpp
std::vector<int> v = {1, 2, 3, 4, 5};
for (auto it = v.begin(); it != v.end(); ++it) {
    if (*it % 2 == 0)
        v.erase(it);  // ❌ UB！erase 后 it 失效
}

// 正确写法：
for (auto it = v.begin(); it != v.end(); ) {
    if (*it % 2 == 0)
        it = v.erase(it);  // erase 返回下一个有效迭代器
    else
        ++it;
}
```

| 容器                    | 导致迭代器失效的操作                                                     |
| ----------------------- | ------------------------------------------------------------------------ |
| vector / string         | `push_back` 可能触发 reallocation；`insert`/`erase` 使后续迭代器全部失效 |
| deque                   | `push_front`/`push_back` 不失效；中间插入/删除使所有迭代器失效           |
| list / forward_list     | 只有被删除元素的迭代器失效                                               |
| map / set / unordered_* | 只有被删除元素的迭代器失效                                               |

### 3.6 错误的定位方法

#### 编译时错误的定位

1. **从第一条错误开始看**：编译器后面的错误往往是第一条错误的连锁反应，修完第一条可能就全好了
2. **逐层排查**：先确认语法（分号/括号），再确认类型（const/non-const、参数个数），最后看模板/重载决议
3. **二分注释法**：不确定错误在哪段代码时，注释掉一半代码再编译，快速缩小范围
4. **最小可复现**：把出错的代码精简到最短能复现的程度，通常在这个过程里自己就发现问题了

```bash
g++ -Wall -Wextra -Werror main.cpp  # 开启所有警告，警告即错误
g++ -E main.cpp > full.ii           # 展开宏，查看预处理后实际代码
```

#### 运行时错误的定位

| 工具/方法                | 适用场景                        | 用法                                          |
| ------------------------ | ------------------------------- | --------------------------------------------- |
| GDB                      | 崩溃、逻辑错误、any 运行时问题   | 见第四章                                      |
| AddressSanitizer         | 内存越界、use-after-free、泄漏  | `g++ -fsanitize=address -g main.cpp`          |
| UndefinedBehaviorSanitizer | 除零、溢出、空指针            | `g++ -fsanitize=undefined -g main.cpp`        |
| valgrind                 | 内存泄漏、未初始化变量          | `valgrind --leak-check=full ./program`         |
| `assert()`               | 逻辑约束不满足，开发阶段捕获    | `#include <cassert>` → `assert(ptr != nullptr)` |
| 日志/`printf`            | 调试难以复现的时序问题          | 加关键位置输出，发版时用宏开关掉              |

```bash
# AddressSanitizer —— 快速定位内存问题（推荐！）
g++ -fsanitize=address -g -O0 main.cpp -o program
./program
# 输出会精确告诉你哪一行、怎样的内存错误
```

#### 链接错误的定位

```bash
# 1. 搜索符号在哪个 .o/库中
nm utils.o | grep foo              # 查看 utils.o 中是否有 foo 函数
nm libmath.a | grep foo            # 查看静态库中是否有 foo
objdump -T libmath.so | grep foo   # 查看动态库导出符号

# 2. 查看当前 .o 需要的未定义符号
nm -u main.o                       # 列出 main.o 中引用了哪些未解析的符号

# 3. 确认 C/C++ 符号名混用问题
nm main.o | grep foo               # C++ 编译的符号有 name mangling
c++filt _Z3foov                    # 解码：void foo() —— 对比看符号名是否正确
```

#### 定位流程总结

```
出错了
 ├─ 编译不过？→ 看第一条报错信息 → 二分注释缩小范围 → 修
 ├─ 链接不过？→ nm 查符号 → 确认库/文件是否正确链接 → 修
 └─ 运行崩了？
     ├─ 段错误？→ AddressSanitizer 或 GDB bt 定位行号 → 检查指针/数组
     ├─ 结果不对？→ 二分注释 + printf/assert 缩小范围 → 找到出错的函数
     └─ 内存泄漏？→ valgrind 或 AddressSanitizer → 找到 new 没有 delete 的位置
```

## 五、头文件 vs .cpp

头文件 = 接口/契约（类定义、函数声明、extern 声明、常量、模板），供多文件共享；`.cpp` = 实现（函数体、变量定义）。`#include` 是文本展开。作用是接口与实现分离、代码复用、增量编译。模板的实现必须放头文件（编译期实例化需要完整定义）。

### 头文件保护（Include Guard）

```cpp
// 传统方式
#ifndef MY_HEADER_H
#define MY_HEADER_H
// ... 头文件内容
#endif

// 现代方式（更简洁，几乎所有编译器都支持）
#pragma once
```

### 应该放在头文件中的内容

| 内容              | 原因                                        |
| ----------------- | ------------------------------------------- |
| 函数声明          | 让其他文件知道函数签名                      |
| 类定义            | 编译需要知道类的布局（成员、大小）          |
| 模板定义          | 编译期实例化必须看到完整定义                |
| `inline` 函数定义 | `inline` 含义之一就是允许在多个翻译单元定义 |
| `constexpr` 常量  | 编译期常量需要在头文件中                    |
| extern 变量声明   | 声明但不定义（定义在 .cpp 中）              |

## 六、声明 vs 定义

|      | 声明（Declaration）         | 定义（Definition）                  |
| ---- | --------------------------- | ----------------------------------- |
| 作用 | 告诉编译器名字和类型        | 实际创建实体（分配存储/提供函数体） |
| 次数 | 可重复多次                  | 一个程序里只能定义一次（ODR 规则）  |
| 示例 | `extern int x;` `void f();` | `int x;` `void f() {}`              |

> 📌 ODR（One Definition Rule）：每个非 inline 函数、全局变量在一个程序中只能有一个定义。

## 七、数据结构及常见复杂度

### 7.1 线性结构

| 数据结构 | 随机访问 | 插入（头/尾/中间）  | 删除（头/尾/中间）  | 适用场景               |
| -------- | -------- | ------------------- | ------------------- | ---------------------- |
| 数组     | O(1)     | O(n) / O(1)* / O(n) | O(n) / O(1)* / O(n) | 频繁随机访问           |
| 单向链表 | O(n)     | O(1) / O(1) / O(n)  | O(1) / O(1) / O(n)  | 频繁头尾增删           |
| 双向链表 | O(n)     | O(1) / O(1) / O(1)  | O(1) / O(1) / O(1)  | 已知位置频繁增删       |
| 栈       | —        | O(1)                | O(1)                | LIFO（递归、括号匹配） |
| 队列     | —        | O(1)                | O(1)                | FIFO（BFS、任务调度）  |

\* 仅动态数组尾部操作，需要扩容时摊销 O(1)。

### 7.2 树形结构

| 结构                 | 查找        | 插入     | 删除     | 特点                       |
| -------------------- | ----------- | -------- | -------- | -------------------------- |
| 二叉搜索树（未平衡） | O(n)        | O(n)     | O(n)     | 退化成链表时最坏 O(n)      |
| AVL 树               | O(log n)    | O(log n) | O(log n) | 严格平衡，查找快           |
| 红黑树               | O(log n)    | O(log n) | O(log n) | 放松平衡，插入删除更快     |
| B/B+ 树              | O(log n)    | O(log n) | O(log n) | 磁盘友好，数据库索引       |
| 堆（优先队列）       | O(1) 取最值 | O(log n) | O(log n) | 只关心最值，不关心整体有序 |
| Trie（字典树）       | O(k)        | O(k)     | O(k)     | k = 字符串长度，前缀匹配   |

> C++ STL 中 `std::map`/`std::set` 用红黑树，`std::priority_queue` 用堆。

### 7.3 哈希表

| 操作 | 平均 | 最坏 |
| ---- | ---- | ---- |
| 查找 | O(1) | O(n) |
| 插入 | O(1) | O(n) |
| 删除 | O(1) | O(n) |

- C++ 中：`std::unordered_map` / `std::unordered_set`（链地址法 + 桶）
- 冲突解决：**链地址法**（每个桶存链表）、**开放寻址法**（冲突时找下一个空位）
- 负载因子（load factor）过高时触发 rehash → O(n) 重新分配和插入

### 7.4 排序算法

| 算法     | 平均       | 最坏       | 最好       | 空间     | 稳定 | 特点                       |
| -------- | ---------- | ---------- | ---------- | -------- | ---- | -------------------------- |
| 快速排序 | O(n log n) | O(n²)      | O(n log n) | O(log n) | ❌    | 实际最快，`std::sort` 核心 |
| 归并排序 | O(n log n) | O(n log n) | O(n log n) | O(n)     | ✅    | 稳定，适合链表/外部排序    |
| 堆排序   | O(n log n) | O(n log n) | O(n log n) | O(1)     | ❌    | 原地排序，内存友好         |
| 插入排序 | O(n²)      | O(n²)      | O(n)       | O(1)     | ✅    | 小数据量/接近有序时很快    |
| 冒泡排序 | O(n²)      | O(n²)      | O(n)       | O(1)     | ✅    | 仅教学意义                 |
| 选择排序 | O(n²)      | O(n²)      | O(n²)      | O(1)     | ❌    | 交换次数最少               |

> 📌 `std::sort` 通常用**内省排序（Introsort）**：快排 + 递归过深切换堆排 + 小数据量切换插入排序。

### 7.5 图算法

| 算法           | 时间复杂度                   | 用途                       |
| -------------- | ---------------------------- | -------------------------- |
| BFS            | O(V + E)                     | 无权最短路径、层次遍历     |
| DFS            | O(V + E)                     | 连通分量、拓扑排序、环检测 |
| Dijkstra       | O((V + E) log V)（二叉堆）   | 非负权单源最短路径         |
| Bellman-Ford   | O(VE)                        | 含负权边的单源最短路径     |
| Floyd-Warshall | O(V³)                        | 全源最短路径               |
| Kruskal        | O(E log E)                   | 最小生成树（稀疏图）       |
| Prim           | O((V + E) log V)             | 最小生成树（稠密图）       |
| 拓扑排序       | O(V + E)（DFS 或 Kahn 算法） | DAG 的任务调度             |

### 7.6 STL 容器选择指南

```text
需要随机访问 + 尾部增删？       → std::vector
需要头尾增删？                  → std::deque
需要在中间频繁插入/删除？       → std::list
需要快速查找 + 有序？           → std::set / std::map
需要快速查找 + 无需有序？       → std::unordered_set / std::unordered_map
需要取最值？                    → std::priority_queue
需要两端操作？                  → std::deque
固定大小小数据？                → std::array
```

> 🌟 **记忆锚点**："数组查快改慢、链表改快查慢、哈希平均 O(1)、树 O(log n)、排序 log n 三兄弟（快归堆）。默认用 vector，90% 的情况够了。"

## 八、智能指针（C++11）

### 8.1 为什么需要智能指针

裸指针的问题：忘记 `delete` → 内存泄漏；`delete` 早了 → 悬空指针；异常抛出时跳过 `delete` → 异常安全问题。

RAII（Resource Acquisition Is Initialization）：资源在构造时获取，在析构时释放。智能指针就是 RAII 在指针上的应用。

### 8.2 三种智能指针

| 指针                 | 所有权       | 何时使用                               |
| -------------------- | ------------ | -------------------------------------- |
| `std::unique_ptr<T>` | 独占所有权   | 绝大多数情况的首选，无额外开销         |
| `std::shared_ptr<T>` | 共享所有权   | 多个地方共享同一对象（有引用计数开销） |
| `std::weak_ptr<T>`   | 不拥有，观察 | 打破 `shared_ptr` 循环引用             |

```cpp
#include <memory>

// unique_ptr：独占
auto p1 = std::make_unique<int>(42);
// auto p2 = p1;              // ❌ 编译错误：不能拷贝
auto p2 = std::move(p1);      // ✅ 可以移动，p1 变为 nullptr

// shared_ptr：共享 — 有引用计数
auto s1 = std::make_shared<std::vector<int>>(100);
auto s2 = s1;                  // 引用计数 = 2，最后一个离开作用域时释放

// weak_ptr：观察者 — 不增加引用计数，用于打破循环引用
std::weak_ptr<int> w = s1;
if (auto sp = w.lock()) {      // lock() 返回 shared_ptr，对象还活着
    // 安全使用
}
```

### 8.3 shared_ptr 的循环引用陷阱

```cpp
struct Node {
    std::shared_ptr<Node> next;
    std::shared_ptr<Node> prev;  // ❌ 两个 Node 互相 shared_ptr 引用 → 引用计数永远不为 0！
};

// 修复：
struct Node {
    std::shared_ptr<Node> next;
    std::weak_ptr<Node> prev;     // ✅ weak_ptr 不增加引用计数
};
```

> 🌟 经验法则：**父子关系用 `unique_ptr`（子归父有），共享用 `shared_ptr`，观察用 `weak_ptr`。**

## 九、常用设计模式

> 设计模式 = 在特定场景下反复出现的代码组织方式的总结，本质是**管理变化**——让改一部分时不需要改其他部分。

### 9.1 单例模式（Singleton）

**目的**：确保一个类只有一个实例，并提供全局访问点。

```cpp
class Logger {
public:
    // C++11 起，局部静态变量初始化为线程安全（Magic Static）
    static Logger& getInstance() {
        static Logger instance;     // 第一次调用时初始化，之后不再创建
        return instance;
    }

    void log(const std::string& msg) { /* 写日志 */ }

private:
    Logger() = default;                           // 禁止外部构造
    ~Logger() = default;
    Logger(const Logger&) = delete;               // 禁止拷贝
    Logger& operator=(const Logger&) = delete;    // 禁止赋值
};
// 使用：Logger::getInstance().log("hello");
```

> ⚠️ 单例本质上是全局变量，滥用会增加耦合、使测试困难。只在真正有"全局唯一"需求的场景使用（如日志器、配置管理器）。

### 9.2 工厂模式（Factory）

**目的**：将对象创建逻辑集中管理，调用方不需要知道具体创建的是哪个子类。

```cpp
// 简单工厂
enum class ShapeType { Circle, Rectangle };

std::unique_ptr<Shape> createShape(ShapeType type) {
    switch (type) {
        case ShapeType::Circle:    return std::make_unique<Circle>();
        case ShapeType::Rectangle: return std::make_unique<Rectangle>();
    }
    return nullptr;
}
// 调用方只依赖 Shape 接口 + ShapeType 枚举，不依赖 Circle/Rectangle 具体类
```

### 9.3 策略模式（Strategy）

**目的**：定义一系列算法，让它们可以互相替换，算法变化不影响使用方。

```cpp
// 策略接口
class SortStrategy {
public:
    virtual void sort(std::vector<int>& data) const = 0;
    virtual ~SortStrategy() = default;
};

// 具体策略
class QuickSort : public SortStrategy {
public:
    void sort(std::vector<int>& data) const override { /* 快排 */ }
};
class MergeSort : public SortStrategy {
public:
    void sort(std::vector<int>& data) const override { /* 归并 */ }
};

// 使用方——只依赖策略接口
class DataProcessor {
    const SortStrategy& strategy_;
public:
    DataProcessor(const SortStrategy& s) : strategy_(s) {}
    void process(std::vector<int>& data) { strategy_.sort(data); }
};
// 运行时切换算法：DataProcessor(MergeSort{}) 或 DataProcessor(QuickSort{})
```

### 9.4 观察者模式（Observer）

**目的**：一个对象（被观察者）状态改变时，自动通知所有依赖它的对象（观察者）。

```cpp
class Observer {
public:
    virtual void update(const std::string& msg) = 0;
    virtual ~Observer() = default;
};

class Subject {
    std::vector<Observer*> observers_;      // 注意：裸指针仅示例
public:
    void attach(Observer* o) { observers_.push_back(o); }
    void notify(const std::string& msg) {
        for (auto* o : observers_) o->update(msg);
    }
};

// 使用：Button 被点击 → notify("clicked") → 所有注册的 Observer 收到通知
```

### 9.5 RAII（资源获取即初始化）

**目的**：利用对象生命周期管理资源——构造时获取，析构时释放。这是 C++ **最核心的惯用法**。

```cpp
// RAII 锁守卫——永远不会忘记解锁（即使抛异常）
class LockGuard {
    std::mutex& mtx_;
public:
    LockGuard(std::mutex& m) : mtx_(m) { mtx_.lock(); }
    ~LockGuard() { mtx_.unlock(); }
};

// std::lock_guard / std::unique_lock 已经是标准库实现
// std::unique_ptr / std::shared_ptr 也是 RAII
// std::fstream 打开文件也是 RAII
```

### 9.6 Pimpl 惯用法（Pointer to Implementation）

**目的**：隐藏实现细节，减少头文件依赖，加快编译速度。C++ 特有的设计模式。

```cpp
// widget.h —— 对外暴露的头文件，非常干净
class Widget {
public:
    Widget();
    ~Widget();                          // 必须在 .cpp 中实现（析构时 Impl 已完整定义）
    void doSomething();
private:
    struct Impl;                        // 只声明，不定义
    std::unique_ptr<Impl> pImpl_;       // 实现细节被隐藏
};
// 使用者看不到 Impl 的内容，Impl 变化不需要重新编译 widget.h 的所有使用者
```

### 9.7 模式选择速查表

| 场景                             | 推荐模式   | 一句话原理                         |
| -------------------------------- | ---------- | ---------------------------------- |
| 全局唯一实例                     | 单例       | 私有构造 + 静态局部变量            |
| 解耦对象创建                     | 工厂       | 把 `new` 集中到一个函数/类         |
| 运行时切换算法/行为              | 策略       | 抽离算法为独立类，依赖接口不依赖实现 |
| 一对多通知                       | 观察者     | 被观察者持有观察者列表，状态变化时遍历通知 |
| 管理资源（内存/锁/文件）         | RAII       | 构造获取 + 析构释放 = 永不泄漏     |
| 隐藏实现/减少头文件依赖          | Pimpl      | 用指向 Impl 的指针代替具体成员     |
| 对已有接口做适配                 | 适配器     | 包一层，把 A 接口转成 B 接口       |
| 给对象动态添加功能               | 装饰器     | 包一层，在不改变原类的基础上叠加行为 |
